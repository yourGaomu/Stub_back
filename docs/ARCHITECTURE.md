# 后端架构

## 1. 系统边界

短链接服务是独立部署的通用服务。Canvas、短链接网页和移动端都是调用方；登录身份、短链规则、权限和用量由本服务管理。PostgreSQL 保存权威业务状态，MinIO 只保存素材对象，Redis 只承担短期状态和限流，不把业务真相放进缓存。

## 2. 代码分层

| 目录 | 职责 | 不负责 |
| --- | --- | --- |
| `cmd/api` | 读取配置、启动 HTTP Server、处理进程信号和优雅退出 | 业务规则、数据库查询 |
| `internal/app` | 应用组合根；建立基础设施、迁移数据库、初始化管理员、构造领域服务、注入路由并管理后台任务生命周期 | DTO 解析、业务判断 |
| `internal/transport/httpapi` | Gin 路由、中间件、请求 DTO 校验、HTTP 状态码与统一错误响应 | 持有外部连接、直接实现核心业务事务 |
| `internal/modules/*` | 按认证、短链、素材、模板、业务授权和日志等业务域组织 DTO、服务与事务 | 读取进程环境变量、创建基础设施客户端 |
| `internal/platform/*` | PostgreSQL、Redis、MinIO、`.env` 等技术适配器 | 决定谁有权访问某个业务资源 |
| `internal/config` | 从环境变量解析并验证启动配置 | 在业务模块中分散读取环境变量 |

### 2.1 依赖方向

`cmd/api -> app -> modules + platform -> 外部依赖`。HTTP 传输层依赖领域服务接口及 DTO，但领域模块不依赖 Gin。应用启动时由 `app` 构造模块服务，再注入 HTTP 路由；后台素材清理任务也由 `app` 创建和关闭。

## 3. 请求处理顺序

### 3.1 管理 API

1. 请求 ID、结构化请求日志及 CORS 中间件建立请求上下文。
2. 认证中间件支持人类 Bearer Session Token 和机器 API Key；API Key 通过状态、有效期、IP、Redis 频率及 PostgreSQL 累计额度校验后生成可信用户身份，并附带唯一 `businessId` 上下文。
3. 功能权限中间件读取用户当前权限；需要业务上下文的路由再检查业务登记状态和用户授权。
4. Handler 将请求绑定到 DTO，拒绝未知 JSON 字段，再调用对应领域服务。
5. 领域服务检查工作空间归属、资源状态和额度，在 PostgreSQL 事务中写入业务变化及审计记录。
6. Handler 返回统一响应 DTO；内部错误写入服务端结构化日志，响应只暴露稳定错误码和请求 ID。

### 3.2 公开短链

`GET /r/{code}` 与口令提交入口不要求登录。服务端按短码找到短链记录，执行有效期、次数、IP、启停及口令规则；首次口令页和错误口令不计次。规则通过后，普通 HTTPS 目标返回原始目标的 302，MinIO 目标返回公网 endpoint 的短期预签名 URL 302。服务端不承诺 302 之后目标站点或下载结果。

## 4. 状态与一致性

### 4.1 PostgreSQL

PostgreSQL 是用户、会话、功能权限、业务授权、邀请码、工作空间、模板版本、素材元数据、短链、访问事件和审计事件的权威存储。对外 ID 使用带类型前缀的 UUID；SQL 值始终参数化。

数据库迁移随二进制嵌入，启动时由 Goose 按版本顺序应用。首位管理员在应用启动过程中初始化；若库中没有管理员且环境变量未提供有效初始管理员信息，服务拒绝启动。

### 4.2 Redis

Redis 当前只存放邮箱验证码发送的短时限流计数。丢失 Redis 数据不应导致用户、短链或权限记录丢失。首期不加入 Kafka：目前的强一致操作由 PostgreSQL 事务完成，单个到期素材清理任务由数据库行锁协调；出现需跨服务订阅、持续消息重放或显著削峰需求后再评估消息队列。

### 4.3 MinIO

MinIO 独立部署并由专用服务端凭据访问。后端用内网 endpoint 上传、查询和删除对象；生成访问签名时使用公网 endpoint，避免把容器地址返回给浏览器。调用业务桶前必须验证业务登记、启用状态及用户授权；API Key 还必须与绑定的单一 `businessId` 一致。

上传流程先在 PostgreSQL 事务中锁定用户额度，再写 MinIO 对象和素材元数据；若数据库提交失败，服务尝试补偿删除对象。素材删除先软删除并进入七天恢复期；后台 worker 通过 `FOR UPDATE SKIP LOCKED` 领取到期记录，MinIO 删除确认成功后才标记物理删除并释放额度。清理失败保留额度、增加重试计数并记录系统审计。

## 5. 运行与运维边界

1. Nginx 在外部代理网络转发 API；后端仅绑定宿主机回环地址。
2. PostgreSQL 与 Redis 位于 Compose 内部网络，不向公网映射端口。
3. MinIO 使用独立的容器网络；后端和 MinIO 通过内网通信。
4. `/healthz` 只表示进程可响应；`/readyz` 检查 PostgreSQL、Redis 和已配置的 MinIO。
5. 数据库审计记录和短链访问事件长期留存；运行诊断日志使用结构化标准输出，由部署环境采集，不混入业务表。

## 6. 扩展约定

### 6.1 新增业务能力

1. 在对应 `internal/modules/{domain}` 中定义请求/响应 DTO 和领域服务。
2. 在 `internal/transport/httpapi` 注册路由，认证、功能权限和业务授权均放在业务 Handler 之前。
3. 由 `internal/app` 构造并注入服务依赖；不要在 Handler 内创建数据库、Redis 或 MinIO 客户端。
4. 需要持久化的权限、额度、规则和审计数据写入 PostgreSQL；Redis 仅用于可过期状态。
5. 增加接口时同步更新 `docs/API.md`，记录作用、权限、入参和出参。

### 6.2 安全日志

业务审计记录操作者、目标、时间、来源 IP、User-Agent、请求 ID、结果和白名单详情。不得记录密码、登录 Token、邮箱验证码、访问口令、MinIO 凭据或预签名 URL。认证失败与成功、权限/额度变更、邀请码、短链、素材、模板和业务授权等事件按业务事务要求写审计；高频诊断信息留在结构化运行日志。
